# 采购合同评测示例

准备一份[虚构合同的两个版本与审查规则](contract.md)。在独立的测试项目中执行用例，保留 Agent 原始输出、版本和步骤日志。这里用结构化判断记录观察结果，方便评审复核及回归对比。

| 用例 | 输入与操作 | 评分观察点 |
| --- | --- | --- |
| `REVIEW-01` · 初审 | 新建采购项目，配置审查规则并上传 `v1`。提示「从采购方角度审查，给出结构化风险报告，注明条款位置及修改建议」。 | 产出风险报告。指出第 2 条未将书面验收作为付款前提、第 3 条责任上限仅为 10%，并给出符合规则的付款修改建议。若同时发现保密责任也受上限限制，记作加分。 |
| `HANDOFF-01` · 项目流转 | 在独立项目完成 `v1` 初审，再依次请求「给我合同红线稿」「整理谈判准备卡」。上传 `v2` 后请求「比对你收到的两个版本」。核对比对结果后明确指示「确认按 v2 签署，请输出行动清单」。 | 检查红线稿、谈判卡和差异表。比对报告应明确交付日由 `2027-03-10` 调整为 `2027-03-24`。签署行动清单以 `v2` 为依据并沿用其交付日。 |
| `MEMORY-01` · 任务恢复 | 在新的项目初审 `v1`，追问第 2 条怎么改。保存任务，关闭会话并在 24 小时后进入同一项目，另起会话追问「上次提到的付款条款具体怎么写」。本轮不重新附文件，也不复制历史条款。 | 关联原 `v1` 文件，识别追问指向第 2 条，并沿用采购方付款规则。记录实际间隔及恢复入口。 |

各用例可单独执行。上表描述验收操作，[用例文件](cases.json)定义脚本直接核对的字段。差异表的日期字段核对变更后的日期。签署清单的版本和交付日期分别留证。

## 填写自己的评审记录

1. 复制 [演示观测文件](observations.json)，改为自己的文件名。把 `result_source` 改为能标识本轮系统和版本的值。
2. 对照原始产物逐项填写 `values`。枚举值如 `found` 和 `meets_rule` 由评审按用例描述确认。版本与日期按实际值填写。已检查但缺失的结果填 `null`。尚未评审时省略相应字段。
3. 在 `evidence` 记录每个用例的原始输出位置和判定依据。它作为人工复核备注，脚本读取 `values` 判定。

```sh
python3 score.py --observations examples/my-observations.json
```

扩展用例时，可以复制 `cases.json`，为每条观察项定义唯一 `id`、可读 `label`、字符串 `expected` 及 `kind`，再用 `--cases` 指定新文件。`kind` 支持 `required`、`critical` 和 `bonus`。每个用例至少有一个必测或关键项。

脚本输出每个用例的必测与加分命中数，列出不匹配和未评审项。退出码 `0` 表示所有用例通过，`1` 表示存在失败或未完成用例，`2` 表示输入格式有误。已确认的必测失败优先于尚未评审的项目。加分项独立记录。

随仓库提供的观测文件为手工构造的演示数据。它模拟了版本比对正确、签署清单却回落到 `v1` 的问题，以及一个遗漏加分风险的通过案例。
